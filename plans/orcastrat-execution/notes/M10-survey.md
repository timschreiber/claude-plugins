## Outline bullet 4: agents/validator.md

- Model/effort/tools per Context `:22` and spec `:228`: `model: sonnet`, `effort: medium`, `maxTurns: 20`, `tools: Read, Glob, Grep, Bash`. Matches D68's shell-allowlist bucket ("Shell for short read-only commands only... `validator`", plan.md `:155`) and spec §22 item 3 bullet "`status-reader` and `validator`: read-only file tools and the shell tool for short read-only commands only. They reply inline and write nothing." (`:501`).
- `agent-files.bats` doesn't yet list `validator` anywhere (`WORKER_AGENTS`/`NON_WORKER_AGENTS`/`NO_SHELL_AGENTS` at lines 8-10) — M10's task must add `validator` to `NON_WORKER_AGENTS` (it has Bash, so not to `NO_SHELL_AGENTS`) and to the `"non-worker agents allow exactly the tools of their role"` test's case statement (`agent-files.bats:193-209`) with `expected='Read, Glob, Grep, Bash'`.
- Closest existing template for a no-notes-file, inline-reply-only agent with model/no maxTurns/no effort variety is `status-reader.md` (haiku, no effort, no maxTurns, replies inline, "Write nothing at all: your reply is your only output" at `status-reader.md:12`) — but validator needs `maxTurns: 20` per Context, unlike status-reader which has none (bats asserts `[ -z "$(field "$f" maxTurns)" ]` at `agent-files.bats:363` for status-reader specifically — validator needs its own analogous test asserting `maxTurns` IS `20`).
- Validator's reply cap: Context `:22` says "replies inline in at most 5 lines, with its score and a one-line reason" — tighter than the generic 20-line cap `agent-files.bats:309-320` enforces for `NON_WORKER_AGENTS`. If `validator` is added to that list, that test would need an exception (mirroring the existing `status-reader` special-case branch at `agent-files.bats:312-317`), or validator needs its own dedicated bats test instead of joining `NON_WORKER_AGENTS`'s generic 20-line check. Spec (`:231`) also caps at 5 lines: "It replies with its score and a one-line reason (at most 5 lines)."
- Input to validator (Context `:23`, spec `:230`): the finding (claim, citation, scenario/rule), the diff or plan section, the same criteria the reviewer had, and paths of any instruction file the finding cites — **never the reviewer's score**.
- Confirms rule statement (Context `:24`, spec `:231`): "For a finding that cites an instruction file, it confirms that the file states that rule."
- No existing dispatch-message convention for "one finding" exists in `run`/`plan` SKILL.md today — this is new plumbing M10's tasks 5/6 add.
